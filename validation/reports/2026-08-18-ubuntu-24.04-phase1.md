# Phase 1 validation report — Ubuntu 24.04.4 LTS (x86_64)

Sanitized record of one complete eight-gate run of
`validation/run-validation.sh` on a Debian-family host. Paths are rewritten to
`<workspace>`, the effective user is rewritten to `<operator>`, and per-file
SHA-256 digests are elided: this is a report, not an archived manifest, so it
carries no digest of generated key material. No passphrase, private-key body,
plaintext, decrypted material, or raw secret value appears here or in the
harness outputs it summarizes.

This run validates the artifacts it generated on this host with these tool
versions. It is not proof of complete format support, and it establishes nothing
about formats whose generator was skipped.

## Findings from this validation

Two harness observations surfaced:

1. `hg_tool_version ssh-keygen` ran `ssh-keygen -V`. `ssh-keygen` has no version
   flag on any platform — `-V` is its certificate validity-interval option — so
   the probe recorded the usage error `option requires an argument -- V` in
   place of a version in the stage 1 inventory, stage 2 plan, and frozen
   manifest. This issue leaves `validation/lib/common.sh` unchanged because it
   is outside the approved file list. OpenSSH 9.6p1 was established separately;
   it is not claimed as the manifest-recorded value.
2. The symlink-rejection self-test patched `Path.stat` unconditionally. On
   Python 3.12+, `Path.is_symlink()` reaches `os.stat` through
   `Path.stat(follow_symlinks=False)`, so the guard fired on the harness's own
   `lstat` and failed the self-test on Python 3.12 while passing on 3.10/3.11.
   The guard now rejects only a stat that follows the link — which is the
   behavior the test exists to forbid. `harness_tool.py` itself was correct.

`validation/lib/env_inspect.sh` mapped `ID=ubuntu` with `ID_LIKE=debian` to
family `debian`. Its production path reads only `/etc/os-release` through an
inert-text parser; self-tests call that parser directly with fixtures, and no
fixture content is sourced or executed. The harness required no RHEL/CentOS
path, no `/etc/redhat-release`, and no `rpm` query. No `apt`,
`apt-get`, `dnf`, `yum`, `zypper`, or `pacman` was invoked anywhere in the run;
package managers appear only as prose in `validation/environments/`.
