# Phase 1 validation report — AlmaLinux 9.8 (x86_64)

Sanitized record of the HG-045 Phase 1 harness on a RHEL-family host. AlmaLinux
is a RHEL-compatible distribution; `/etc/os-release` reports
`ID=almalinux` with `ID_LIKE="rhel centos fedora"`, which is what
`lib/env_inspect.sh` matches. Red Hat Enterprise Linux itself and CentOS Stream
were **not** run; see the limitations section.

Paths are rewritten to `<workspace>`, `<checkout>`, and `<home>`, the effective
user is rewritten to `<operator>`, the run ID is rewritten to `<run-id>`, and
per-file SHA-256 digests are elided: this is a report, not an archived manifest,
so it carries no digest of generated key material. No passphrase, private-key
body, plaintext, decrypted material, or raw secret value appears here or in the
harness outputs it summarizes.

Two runs are recorded below. Run 1 halted inside stage 7 on a dependency-version
defect and is reported in full rather than discarded. Run 2 is the complete
eight-gate run. Sanitized transcripts of both are in
[`../transcripts/`](../transcripts/).

This run validates the artifacts it generated on this host with these tool
versions. It is not proof of complete format support, and it establishes nothing
about formats whose generator was skipped.

`rhel.md` warns that RHEL 9 OpenSSL 3 generally needs `openssl genrsa
-traditional` for legacy encrypted PEM, and that FIPS policy may make legacy
encryption unavailable altogether. On this host the generator's first attempt —
`openssl genrsa -aes128 -traditional` — succeeded, the artifact carried
`Proc-Type: 4,ENCRYPTED`, and the scan matched it as
`private_key:legacy_pem_encrypted`. No legacy-PEM skip was recorded, and the
FIPS fallback path in that note was therefore not exercised.

## Findings from this validation

1. **Stage 7 aborts the whole run when `rule_id` is a float NaN
   (run 1).** With dependencies resolved as of this date — pandas 3.0.5, numpy
   2.5.2 — `harvestguard scan --json` writes `NaN` for findings that carry no
   rule ID. `harness_tool.py summarize` normalizes a missing rule ID with
   `finding.get("rule_id") or "(none)"`, and NaN is truthy, so the NaN survives
   into `sorted(by_rule.items())` and raises
   `TypeError: '<' not supported between instances of 'str' and 'float'`.
   `run-validation.sh` runs under `set -e` and does not guard that call, so the
   harness exited 1 in the middle of stage 7 — after the scans had run and
   `results/` was populated, but before the stage 7 gate, the stage 8 gate,
   comparison, and the cleanup prompt. The full transcript is
   [`../transcripts/2026-08-18-almalinux-9.8-phase1-halted-run.txt`](../transcripts/2026-08-18-almalinux-9.8-phase1-halted-run.txt).

   This is not RHEL-specific. The cause is the pandas major version, confirmed
   on this same host: `rule_id` arrives from a pandas row in
   `finding_adapters.py`, and re-scanning the identical frozen corpus with
   pandas 2.3.3 produced 8 `None` rule IDs where pandas 3.0.5 produced 8 NaN.
   Any host that resolves pandas 3.x hits it. Fixing it would mean editing
   `validation/harness_tool.py` or product code, both outside this issue's
   approved file list, so nothing was changed.

2. **Run 2 pinned pandas below 3.0 to get past that defect.** The complete
   eight-gate run recorded above used pandas 2.3.3 with numpy 2.5.2, installed
   as operator preparation before the harness started. Everything else about the
   two runs was identical, and both produced the same 17 findings and the same
   asset-type distribution. The eight-gate result therefore describes a
   pandas 2.x environment; a fresh `pip install harvestguard` today resolves
   pandas 3.x and stops at stage 7.

3. **`hg_tool_version ssh-keygen` still reports a usage error**, as on Ubuntu:
   the probe runs `ssh-keygen -V`, which is the certificate validity-interval
   option rather than a version flag. AlmaLinux additionally returns it with a
   trailing newline, so the recorded value spans two lines in the stage 1
   inventory. `validation/lib/common.sh` is outside this issue's approved file
   list and was left unchanged.

`validation/lib/env_inspect.sh` mapped `ID=almalinux` with
`ID_LIKE="rhel centos fedora"` to family `rhel` — the first recorded exercise of
the RHEL branch of that `case`. Its production path reads only
`/etc/os-release` through an inert-text parser. The harness required no
`/etc/redhat-release` file and no `rpm` query. No `dnf`, `yum`, `apt`,
`apt-get`, `zypper`, or `pacman` was invoked anywhere in either run; package
managers appear only in the separate operator-preparation step and as prose in
`validation/environments/`.

## Limitations

- AlmaLinux 9.8 only. Red Hat Enterprise Linux, CentOS Stream, and Rocky Linux
  were not run. They share the `ID_LIKE` values this harness matches, but that
  is an inference from the detection code, not an observation.
- A container, not a bare-metal or VM install. Privilege, volume-level, and
  `systemd-detect-virt` observations would differ on a full install, and the
  kernel reported by `uname` is the container host's.
- `x86_64` only; `aarch64` and `ppc64le` RHEL-family builds are unvalidated.
- FIPS mode was off. The FIPS-restricted legacy-encryption path described in
  `environments/rhel.md` remains unexercised.
- The complete run required pandas below 3.0 (finding 2 above). The default
  dependency resolution on this date does not complete stage 7.
- Only `--type crypto` was scanned. Other scan types were not exercised.
- The `age_encrypted` generator is unvalidated on this family, because `age` was
  absent.
- One host, one set of tool versions, one corpus. It validates those bytes on
  that host, not the format families in general.
