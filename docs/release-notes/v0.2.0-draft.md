## HarvestGuard v0.2.0 — Cryptographic Inventory and First Public Use

HarvestGuard is an open-source cryptographic asset inventory and
evidence-collection tool for technology due diligence. It records what
cryptographic material and sensitive-data placement it can observe, with
provenance, so a reviewer can read the evidence themselves.

This is a **pre-1.0 release**. CLI flags, report sections, and documentation may
change between versions; the normalized finding schema is versioned separately
(`schema_version`).

### What changed

**Broader cryptographic asset inventory.** Bounded, format-specific detectors
that require structural evidence rather than a filename extension or an entropy
guess:

- encrypted files and containers — OpenSSL `Salted__`, binary and
  ASCII-armored OpenPGP messages, gocryptfs forward-mode cipher roots (reported
  once per root, without mounting), and native age v1 files;
- encrypted key and object structures — encrypted PKCS#8 private keys,
  CMS/PKCS#7 encrypted objects, and legacy PEM encryption headers;
- keystores and certificate stores — BCFKS and JCEKS keystores, Mozilla NSS
  database sets, and Java trusted-certificate-only stores;
- host and cluster identity material — OpenSSH host identity (file-local
  private-key, public-key, and host-certificate findings) and Kubernetes TLS
  Secret manifests read from local JSON and YAML files only.

**Clearer scan accounting.** Ordinary files no longer generate repeated
per-file filesystem context findings; shared filesystem context is reported
once per mount or volume, and summaries separate material evidence, aggregate
context, coverage limitations, skipped entries, finding-level errors, and
scanner errors.

**A first run you can trust.** A synthetic demo corpus, committed sample JSON
and Markdown output from exactly that demo scan, a README quickstart, and an
executive-readable evidence example whose every statement traces back to a
technical finding.

**Installation that works from a clean environment.** `pip install .` produces
a usable `harvestguard` command without a second dependency step.

Internally: a shared crypto detector framework and an internal-only
cryptographic relationship model. Neither appears in JSON or Markdown output.

The full entry is in [CHANGELOG.md](../../CHANGELOG.md).

### How to try it

```bash
git clone https://github.com/serewicz/HarvestGuard.git
cd HarvestGuard
python3 -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate
python -m pip install .

# Review a scan of the synthetic demo target
harvestguard scan demo/sample_target --type all --summary

# Export the same scan as evidence artifacts (two separate runs)
harvestguard scan demo/sample_target --type all --json findings.json
harvestguard scan demo/sample_target --type all --markdown report.md
```

Python 3.10+ is required. All three commands exit `0`. The demo deliberately
produces one finding-level error — a fake PEM body reported as a
low-confidence `Malformed PEM Private Key` — which is expected output, not a
failure. The [README Quickstart](../../README.md#quickstart) explains what to
expect, including which values are host-dependent.

To see the output before installing anything, read
[docs/examples/first-run/](../examples/first-run/README.md).

**Distribution.** Install from this source checkout. HarvestGuard is **not
published to PyPI**, so this release has no wheel or sdist. Container images
are published from `main` and identified by commit SHA and digest, not by
product version:

```bash
docker pull ghcr.io/serewicz/harvestguard:<commit-sha>
```

The image runs the Streamlit dashboard only; the CLI is not available inside
it. Verification commands for its signature and SBOM attestation are in
[SECURITY.md](../../SECURITY.md#verifying-the-container-image).

### What this release does not claim

HarvestGuard is **evidence only**. A finding records what was structurally
observed in a file or reported by a cloud provider's API. It does not
establish, and this release does not claim:

- complete or exhaustive inventory of cryptographic material;
- that absence of a finding proves absence of cryptographic material;
- runtime exposure or exploitability;
- business risk, financial impact, or executive priority;
- compliance or audit conclusions;
- remediation advice or remediation priority;
- migration readiness or quantum readiness;
- HNDL (Harvest Now, Decrypt Later) exposure or any risk score in CLI output.

Risk Score and HNDL Exposure exist only in the optional Streamlit dashboard,
are labeled heuristic and `Needs Validation`, and appear in no JSON or Markdown
artifact. CLI reports carry no risk score, no remediation advice, no business
impact, no compliance conclusion, and no quantum-readiness verdict, by product
boundary
([ADR-006](../DECISIONS/ADR-006-product-boundary.md)).

### Known limitations

- **Absence of a finding is not proof of absence.** Every detector recognizes
  specific structures in specific formats; anything outside them is not
  detected. Per-scanner misses, likely false positives and false negatives, and
  how to read `confidence` are in
  [docs/DETECTION_CHARACTERIZATION.md](../DETECTION_CHARACTERIZATION.md).
- Keystore, NSS, and truststore findings are structural evidence about the
  container, not a decrypted enumeration of its contents. Encrypted material
  may not expose algorithm or key-size metadata without a passphrase.
- Kubernetes TLS Secret evidence comes from local manifest files only; it says
  nothing about what a live cluster holds. OpenSSH findings are file-local, with
  no cross-file key/certificate pairing.
- Cloud object encryption status is **provider-reported metadata** (S3, GCS,
  Azure Blob), not independent proof of the underlying cryptographic
  implementation.
- Crypto code analysis covers **Python source text only** — no binary,
  bytecode, runtime, or network/TLS discovery. A code-analysis execution
  failure writes its diagnostic to stderr only, so from the artifact alone it
  is indistinguishable from a clean scan.
- Local scans are depth-bounded by default (`--max-depth 3`). A bounded or
  partial scan is stated in the artifact's *Coverage*, *Scope*, and *Errors and
  Warnings* sections rather than silently.
- Sensitive-data findings report category and count only, never the matched
  values. Reports can still contain sensitive identifiers — file paths, bucket
  and object names — so handle and share them accordingly.
- Detection has been exercised against the repository's own fixtures and demo
  corpus; **real-world validation depth remains outstanding work** and no claim
  above depends on it.
- Release engineering remains pre-1.0: no lock file or hash-pinned
  requirements, no source/package SBOM, no SLSA provenance attestation, no
  signed tags, no published wheel, and no version-tagged container image. See
  [docs/RELEASE.md](../RELEASE.md#sbom-signing-and-provenance-status).
- Not built: CBOM (CycloneDX) and PDF export, network/TLS cipher discovery, and
  the packaged Technology Due Diligence Evidence Package.

### Support

Support is **best effort through GitHub Issues, with no service-level
agreement, no guaranteed response time, and no paid support tier**. Only `main`
is supported; there are no release branches and no backports. See
[SUPPORT.md](../../SUPPORT.md). Report security vulnerabilities privately per
[SECURITY.md](../../SECURITY.md) rather than in a public issue.

Scan only targets you are authorized to scan.
